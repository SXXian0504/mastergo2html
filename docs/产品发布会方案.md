## 1. 产品命名与定位

### 推荐产品名

**MasterGo2Code**

原因：当前能力已经从单页 HTML 延伸到多页面 React 项目，`MasterGo2HTML` 更适合作为内部模块名，`MasterGo2Code` 更能覆盖完整产品边界。

备选：

1. **MasterGo2Web**：更面向设计师，强调最后得到网页。
2. **FrameFlow**：品牌感更强，但首次听到不容易理解功能。
3. **Design to Project**：强调工程结果，但名字较通用。

### 推荐一句话介绍

> **让设计师从 MasterGo 设计稿直接获得高保真、可运行、可继续开发的网页与 React 项目。**

更短的发布会主张：

> **从设计稿，到可运行项目。**

### 产品边界

它解决的是“设计交付到前端第一版”之间的空白，不是替代前端完成业务接口、复杂状态和生产发布。

不要说：

> 一键把设计稿变成可以直接上线的网站。

建议说：

> 把设计稿转换成可运行、可验证、可继续开发的第一版网页和 React 工程。

## 2. 发布会核心故事

### 核心冲突

今天“设计稿转代码”已经不新鲜，但设计师仍然面临两个问题：

1. 直接使用设计稿转代码插件，复杂素材、蒙版、布局关系容易丢失或错位。
2. 使用通用 Agent 时，需要设计师输入大段 Prompt、反复补充上下文，并承担更高的时间和 Token 成本。

### 问题重构

> **设计师不应该为了生成一个页面，先学会如何指挥 AI。**

问题并不是模型不会写 HTML，而是单个 Prompt 很难同时承载：

- 设计节点结构；
- 素材及蒙版关系；
- 文本、颜色、字体与间距；
- 布局和响应式规则；
- 页面交互和跳转；
- 多页面之间的路由与复用关系；
- 生成结果与原设计稿之间的视觉验证。

### 产品洞察

> 高质量设计稿转代码，不是一次生成问题，而是一条工作流问题。

因此产品没有要求用户写一个“更好的 Prompt”，而是把任务拆成一条可重复流程：

```text
MasterGo 设计事实
      ↓
节点、文本、样式、素材和页面截图
      ↓
布局 / 组件 / 素材 / 交互分阶段分析
      ↓
单 Frame 高保真 HTML
      ↓
逐页视觉验证
      ↓
多页面合并为 React 工程
      ↓
路由、组件、类型检查、构建和视觉回归验证
```

### 最终价值

- 对设计师：减少写 Prompt、找素材和解释设计稿的工作。
- 对前端：从可运行、可继续开发的首版开始，而不是从空目录开始。
- 对团队：降低设计意图在交接过程中丢失的概率。

## 4. 逐页 Slide 结构

### Slide 01｜封面

**标题：**

> 设计师不该为了生成页面，先学会写 Prompt

**副标题：**

> MasterGo2Code · 从设计稿，到可运行项目

**讲述：**

> 今天，设计稿转代码已经不是一个新概念。但当设计师真正把设计稿交给生成工具后，常常还要补 Prompt、找回丢失的素材，再把错位的布局重新改回去。如果最后仍然需要设计师重新解释一遍自己的设计，生成工具就没有真正理解设计稿。

**视觉：** 深色或暖白背景；MasterGo Frame 轮廓在左侧，网页轮廓在右侧，中间只有一条细的转换路径。

**动效：** Frame 和网页先后淡入，中间路径最后出现。

### Slide 02｜现有路径看起来很短

**标题：**

> 看起来，只需要把设计稿交给 AI

**视觉：**

```text
设计稿 → AI → 代码
```

**讲述：**

> 从流程图上看，这件事只有三步。但实际使用时，中间隐藏了大量需要人工补充的信息。

**动效：** 先只显示三步，随后三步之间逐渐拉开距离。

---

### Slide 03｜真实路径远比想象中长

**标题：**

> 真正被消耗的，是设计和代码之间的间隙

**内容：**

```text
选中设计稿
→ 编写长 Prompt
→ 补充素材
→ 解释布局
→ 修复错位
→ 处理蒙版/SVG
→ 补响应式
→ 再次生成
→ 人工合并页面
```

**视觉：** 一条越来越长的工作流；不要使用普通项目符号列表。

---

### Slide 04｜展示具体失败，而不是抽象评价

**标题：**

> “生成成功”，不等于“设计被正确理解”

**展示两个最有说服力的案例：**

1. 页尾 Logo：竞品/普通 MCP 结果显示为黑框，本产品正常恢复蒙版和素材。
2. 页面布局：竞品出现错落，本产品主要布局关系与设计稿保持一致。

**版式：** 三列并排：设计稿 / 对照方案 / MasterGo2Code。

**讲述原则：** 不攻击竞品，只说明相同输入条件下的可观察差异。

**动效：** 先显示设计稿，再依次揭示两个结果；使用局部放大强调 Logo 和错位区域。

---

### Slide 05｜问题重构

**标题：**

> 问题不在于 Prompt 不够长

下一次点击后出现：

> 而在于设计事实没有完整进入生成过程

**讲述：**

> 一个截图告诉模型页面长什么样，但它不一定能告诉模型节点是什么、素材来自哪里、蒙版如何组合、哪些元素属于同一个模块，以及多个页面之间应该怎样形成路由。

---

### Slide 06｜产品原则

**标题：**

> 不让设计师解释设计稿，让产品读取设计稿

三个原则：

1. **Design Facts First**：先采集节点、文本、样式、资源和截图。
2. **Workflow, Not Prompt**：把复杂任务拆成稳定、可追踪的阶段。
3. **Verify Every Output**：生成后回到设计稿做视觉验证。

---

### Slide 07｜产品 Reveal

**标题：**

> MasterGo2Code

**副标题：**

> 从 MasterGo Frame，到可运行项目

**讲述：**

> 基于这三个原则，我做了 MasterGo2Code。它不是一个更长的 Prompt，也不是只生成一段代码，而是一条从设计事实采集到工程验证的完整工作流。

**动效：** 使用一次较慢的蒙版 Reveal 或 Magic Move；这是全场唯一一个可以稍有发布感的产品登场动画。

---

### Slide 08｜两种入口，一条工作流

**标题：**

> 在 MasterGo 里开始，或者交给本地 Agent

**内容：**

- MasterGo 插件：选中 Frame 后直接提交生成任务。
- Agent Skill：让本地 Agent 按固定流程完成单页生成与多页工程合并。

**重点：** 用户不需要每次重新组织大段 Prompt。

**视觉：** 两条入口最终汇合到同一条生成管线。

---

### Slide 09｜系统不是一步生成

**标题：**

> 每个阶段，只解决一个明确问题

**展示：**

```text
采集设计事实
→ 还原静态资源
→ 分析布局
→ 规划组件
→ 推理交互
→ 生成 HTML
→ 截图验证
```

**讲述：**

> 这种拆分增加了过程的可追踪性。出现问题时，可以判断是素材、布局、交互理解还是最终代码生成出了问题，而不是只能重新发送整段 Prompt。

**动效：** 阶段逐个点亮，避免所有节点同时运动。

---

### Slide 10｜主 Demo：一个 Frame 变成网页

**标题：**

> 现在，把一个真实页面交给它

**Demo 形式：全程播放经过剪辑的实操视频，不进行现场操作。**

将 Demo 拆成两条递进链路：

1. **链路 A：MasterGo 插件 → 单页 HTML**
   - 在 MasterGo 中选中完整页面 Frame；
   - 打开插件并提交生成任务；
   - 压缩展示设计采集、素材处理、布局分析和 HTML 生成阶段；
   - 打开生成结果，从首屏滚动到底部；
   - 展示蒙版 Logo、主要布局、交互和基础响应式。
2. **链路 B：本地 Agent + Skill → 多页 React 项目**
   - 用户只输入一句简短任务，不再编写大段 Prompt；
   - Agent 读取固定 Skill，逐 Frame 生成并验证 HTML；
   - 将多个 HTML 合并为带路由的 React / Next.js 项目；
   - 展示路由跳转、工程结构、构建结果和视觉验证。

**注意：** 两条链路分别剪成独立视频，中间由演讲者停下来总结价值。不要连续播放一段 6–8 分钟的长视频。

### Slide 11｜Hero Moment：素材没有消失

**标题：**

> 复杂素材，不应该在转换中变成一个黑框

**展示：** 页尾 Logo 或蒙版图标的设计稿、对照结果、本产品结果。

**讲述：**

> 这个 Logo 不是一张可以直接引用的普通图片，它包含蒙版和组合关系。普通链路容易把它理解成黑色占位区域。产品在采集阶段保留素材和渲染证据，因此最终可以恢复正确外观。

**动效：** 先展示整个页尾，再把 Logo 区域放大；不要让三个版本同时飞入。

---

### Slide 12｜不只是看起来像

**标题：**

> 从一张页面，继续走向一个工程

**内容：**

- 每个 Frame 独立生成并验证 HTML。
- 多个页面映射为独立路由。
- 合并为 Next.js / React 工程。
- 保留页面结构和静态资源。
- 完成 lint、TypeScript 检查和生产构建。
- 在组件复用后继续进行视觉回归。

**视觉：** 三个独立页面卡片进入同一个 React 工程框架，而不是展示代码墙。

---

### Slide 13｜结果证据

**标题：**

> 结果需要被测量，而不是只靠“看起来不错”

目前仓库内可以安全使用的证据：

- 已有三条真实页面路由被合并为 Next.js App Router 项目。
- 结构校验、ESLint、TypeScript 检查和生产构建通过。
- HTML 到 React 的视觉差异指标最高约为 `0.0061`，说明工程迁移基本没有引入新的视觉偏差。
- 已记录的近期正常成功样例通常约为 13–18 分钟；复杂、异常或中断任务可能明显更久。
- 支持静态素材、主要布局、简单交互推理和基础响应式处理。

不要直接写“视觉还原度 >95%”，除非先定义指标、样本量、截图视口和计算方式。

建议拆成四类数据：

1. **生成成功率**：多少任务完成并通过静态校验。
2. **素材完整率**：设计稿引用素材中多少被正确输出。
3. **视觉差异指标**：统一视口下的截图差异。
4. **工程通过率**：lint / typecheck / build / route smoke 是否通过。

- AI 分阶段工作流；
- HTML 生成与静态校验；
- Agent Skills 和 CLI；
- 多页面 React 工程合并；
- 视觉回归和工程验证。

**讲述：**

不要只强调“代码都是我写的”，重点强调你定义了产品问题，并把跨多个系统的链路真正跑通。

### Slide 15｜诚实地说明边界

**标题：**

> 它已经能完成第一版，但还没有替代完整开发

当前边界：

- 复杂业务接口仍需开发接入；
- 复杂状态和动态数据不能仅靠静态设计稿完整推理；
- 特殊字体、复杂特效和极端布局仍可能产生视觉差异；
- 生成时间受到页面复杂度、模型和网络影响；
- React 工程仍需项目团队按真实业务规范继续开发。

**讲述：**

> 明确边界不会削弱产品，反而说明我们知道它当前最适合进入哪一个真实环节。

## 5. 开场 90 秒完整话术

> 今天，设计稿转代码已经不再是一个新概念。
>
> 但当设计师真正把设计稿交给生成工具后，经常还要做三件事：写一段足够长的 Prompt，找回生成过程中丢失的素材，再把错位的布局重新调整回来。
>
> 我在测试现有方案时发现，有些使用蒙版和组合关系的 Logo 会直接变成黑框；有些页面虽然生成成功，布局关系却已经发生变化。另一种方式是把设计稿接入通用 Agent，但这意味着设计师需要不断解释页面结构、资源、响应式和交互，还会消耗更多 Token。
>
> 如果最终仍然需要设计师重新解释一遍自己的设计，那么生成工具并没有真正理解设计稿。
>
> 所以我重新思考了这个问题：高质量的设计稿转代码，可能并不是一次生成问题，而是一条工作流问题。
>
> 今天我想发布的是 MasterGo2Code。一条从 MasterGo 设计事实采集开始，经过布局、素材和交互分析，生成高保真 HTML，并进一步形成 React 项目的完整工作流。

## 6. Demo 编排

### 采用全程预录，不做任何现场生成

本次发布会以结果稳定和叙事完整为优先。所有操作、生成过程和结果检查都提前录制、剪辑并导出为本地 MP4。现场只负责播放和讲解，不依赖网络、模型服务、MasterGo 插件连接或临时任务状态。

预录不需要伪装成实时。可以在视频角落明确标注：

> 实际生成过程经时间压缩，原始任务耗时 XX 分钟。

这会比假装实时更可信。

### 两条链路的叙事关系

两条链路不要作为两个功能并列介绍，而要形成递进：

```text
链路 A：证明“一个设计稿可以可靠地变成一个网页”
                         ↓
链路 B：证明“多个网页可以继续形成一个可开发的工程”
```

#### 链路 A｜MasterGo 插件 → 单页 HTML

回答的问题：

> 设计师不写长 Prompt，能不能从当前设计稿稳定获得一个高保真网页？

核心价值：低门槛、设计事实完整、复杂素材不遗漏、结果可检查。

#### 链路 B｜本地 Agent + Skill → 多页 React 项目

回答的问题：

> 如果设计师或前端已经在使用 Agent，这条能力能不能变成一套可复用的工程流程？

核心价值：一句简短指令触发固定工作流；逐页生成和验证；多页路由合并；工程检查。

### 推荐剪成两个独立视频

#### 视频 A：设计稿到 HTML（2 分 30 秒～3 分钟）

| 时间 | 画面 | 讲述重点 |
|---|---|---|
| 00:00–00:12 | 原始设计稿全貌，快速定位页尾 Logo | 建立视觉基准 |
| 00:12–00:30 | 选中 Frame、打开插件、选择网页端、提交 | 用户只需要完成一次明确操作 |
| 00:30–00:50 | 任务阶段快速流转，右上角标注“实际耗时 XX 分钟” | 不是一次黑盒生成，而是分阶段工作流 |
| 00:50–01:15 | 设计事实、素材、布局、交互等中间阶段蒙太奇 | 产品读取设计，而不是让用户重复解释 |
| 01:15–01:55 | 生成页面完整滚动 | 先让观众建立整体效果印象 |
| 01:55–02:20 | 蒙版 Logo、复杂素材、主要布局局部对比 | 展示最强 Hero Case |
| 02:20–02:40 | 一个交互和一个窄视口响应式结果 | 说明不只是静态截图 |
| 02:40–02:50 | 定格：设计稿与 HTML 并列 | 收束“一个 Frame 到一个网页” |

视频播放结束后暂停 30–45 秒，由演讲者总结：

> 这条链路解决的是单页生成：设计师不需要组织一段复杂 Prompt，插件直接采集当前 Frame 的节点、素材和视觉证据，再通过固定流程得到可运行网页。刚才的蒙版 Logo 是一个很小但很典型的例子——素材是否被正确理解，决定了生成结果是“有代码”，还是“真正保留了设计”。

#### 视频 B：多个页面到 React 项目（2 分 30 秒～3 分钟）

| 时间 | 画面 | 讲述重点 |
|---|---|---|
| 00:00–00:15 | 三个 MasterGo 页面并列出现 | 从单页进入多页面场景 |
| 00:15–00:35 | Agent 中输入一句简短指令 | 不再编写和维护大段 Prompt |
| 00:35–00:55 | Skill 被读取，工作流步骤展开 | 专业方法被固化在 Skill 中 |
| 00:55–01:25 | 三个 Frame 分别生成 HTML，并出现各自视觉验证状态 | 每个页面独立生成、独立验收 |
| 01:25–01:50 | 三个 HTML 汇入 React / Next.js 项目 | 从页面结果进入工程结构 |
| 01:50–02:20 | 浏览器内依次跳转首页、列表、详情 | 展示真实路由与页面连接 |
| 02:20–02:40 | 工程目录、lint、typecheck、build 状态快速出现 | 证明结果可继续开发 |
| 02:40–02:55 | 三个路由最终画面并列 | 收束“从页面到项目” |

视频播放结束后暂停 30–45 秒，由演讲者总结：

> 第二条链路不是重复生成三个页面，而是把单页能力推进到工程。Skill 固化了逐页生成、截图验证、路由映射、React 合并和工程检查的步骤。用户只需要说明目标，不需要重新告诉 Agent 每一步应该怎样做。

### 视频剪辑原则

1. **先展示结果，再解释过程。** 每条视频开头 3–5 秒可以闪现最终结果，降低观众等待感。
2. **鼠标移动全部去掉无意义轨迹。** 光标只在点击前出现，点击后立即进入下一动作。
3. **终端不要长时间占满屏幕。** 终端主要用于证明 Skill 启动、任务阶段和构建通过，不用于让设计师阅读日志。
4. **真实等待全部压缩。** 用阶段时间轴表达过程，不使用几十秒倍速终端滚动。
5. **关键结果必须停顿。** 蒙版 Logo、三方对比、路由跳转和构建通过分别停留 1.5–2 秒。
6. **屏幕录制统一尺寸。** MasterGo、浏览器和 Agent 录制使用相同的 16:9 输出画布。
7. **统一缩放和字幕。** 操作区域放大 110%–130%，字幕不超过两行。
8. **保留真实耗时。** 视频可以压缩，但字幕要注明原始任务时间。
9. **不要配持续背景音乐。** 现场以演讲者讲述为主；只在产品 Reveal 或章节切换使用极轻的声音提示。
10. **导出本地 MP4。** 使用 H.264、1080p，并在实际演示电脑上完整播放测试。

### Slide 与视频的衔接

不要让视频自己承担全部解释。推荐节奏：

```text
提出问题的 Slide
→ 播放视频 A
→ 停止视频，展示蒙版 Logo 三方对比 Slide
→ 解释为什么结果不同
→ “如果不是一个页面呢？”过渡 Slide
→ 播放视频 B
→ 停止视频，展示验证数据 Slide
```

这样视频负责“证明它确实发生了”，Slide 负责“解释它为什么重要”。

### 两条视频的文件准备

建议最终导出：

```text
01-mastergo-to-html-main.mp4
01-mastergo-to-html-backup.mp4
02-pages-to-react-main.mp4
02-pages-to-react-backup.mp4
```

主版本可以带关键字幕，备用版本使用更保守的编码参数。另准备每个视频关键节点的静态截图；即使播放器出现问题，也可以用 Slide 完成讲解。

## 7. 数据口径与验证任务

### 发布前必须做

建立表格记录至少 5 个代表性页面：

| 页面 | 复杂度 | 模型 | 总耗时 | 输入 Token | 输出 Token | 估算成本 | 静态校验 | 素材完整 | 视觉差异 |
|---|---|---|---:|---:|---:|---:|---|---|---:|

### 当前不建议使用的口径

- “转换率 >95%”：转换率含义不清楚。
- “还原度 >95%”：现有视觉报告并不支持所有页面统一达到该数值。
- “每页固定 20 分钟”：实际耗时存在波动。
- “每页固定 3–6 元”：尚未建立 Token 与价格日志。

### 推荐口径

> 在近期正常成功样例中，单页生成通常约 13–18 分钟；具体耗时会受到页面复杂度、模型服务和网络状态影响。

> 当前验证样例中，系统能够完整输出主要文本与静态素材，并保持主要布局关系；复杂特效仍需通过截图差异继续校正。

> 在已有三页工程样例中，HTML 合并为 React 后的视觉差异指标最高约为 0.0061，且 lint、类型检查和生产构建通过。

## 8. 视觉方向

### 推荐概念：Design Evidence / 设计证据

视觉关键词：

- Frame；
- 节点边界；
- 锚点；
- 连接线；
- 图层；
- 截图局部；
- 代码结构；
- 视觉差异框。

不要做传统“AI 蓝紫渐变 + 发光球”。产品真正的差异不是模型本身，而是对设计事实的完整采集与验证。

### 色彩建议

- 背景：`#F7F7F5` 暖白或 `#0D0F12` 深黑；
- 正文：`#111318` / `#F5F7FA`；
- 强调色：高饱和蓝 `#356CFF`；
- 结果成功：绿色只在验证状态使用；
- 差异/问题：红色只在竞品差异或错误标记使用。

### 字体与版式

- 中文可优先使用思源黑体、HarmonyOS Sans SC 或系统黑体；
- 标题 48–64 pt；
- 正文 24–30 pt；
- 使用 12 列网格；
- 每页只保留一个结论；
- 产品截图至少占页面宽度的 60%；
- 代码只显示能支持当前结论的 3–8 行。

## 9. 动效系统

全套只使用四种动效：

1. **Fade**：文字和普通元素出现；
2. **Morph / Magic Move**：Frame、网页、React 项目之间的关系变化；
3. **Mask Reveal**：章节切换和产品 Reveal；
4. **Focus Zoom**：放大 Logo、蒙版、布局差异等局部证据。

节奏建议：

- 普通出现：0.25–0.4 秒；
- 位移/Morph：0.45–0.7 秒；
- 产品 Reveal：0.8–1.0 秒；
- 连续节点错峰：每个间隔 0.08 秒左右。

原则：

> 一次动画只解释一个关系，一页同时只有一个运动焦点。
