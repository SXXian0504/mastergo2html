# MasterGo2HTML 客户演示脚本

## 一、演示目标

这次交流不只是展示“一键生成”，还要确认客户现有设计交接流程里最耗时、最容易返工的环节，并判断插件最适合先进入哪个真实场景。

建议时长：30-40 分钟。现场生成近期样例通常约 10-20 分钟，实际耗时会受页面复杂度、素材大小、模型服务和网络状态影响，不把完成时间作为承诺。

核心口径：插件当前生成的是可运行、可继续开发的 HTML/CSS/JS 初稿，不是未经开发验收即可直接上线的完整业务系统。

## 二、演示前准备

### 必须准备

1. 提前启动本地服务，确认 `http://127.0.0.1:12322/health` 可访问且模型配置正常。
2. 在 MasterGo 中准备一个结构清楚、素材完整、大小适中的单页面 Frame。
3. 提前完整跑一遍同一 Frame，保留成功结果作为现场兜底。
4. 准备 2 个竞品结果，尽量使用与本插件相同的设计稿、相同视口和相同输入条件。
5. 准备 2-3 个本插件历史结果，至少包含设计图截图、生成页面和输出代码。
6. 关闭无关通知，提前打开任务面板、历史结果目录和浏览器预览页。

### 建议使用的本地案例

- 岗位详情设计图：`.mastergo2html/jobs/05a7657a-b2fc-4eaf-a9ad-7074bd3335b0/00-input/frame-screenshot.png`
- 岗位详情生成效果：`.mastergo2html/jobs/257b5c1e-43f1-4617-81c4-21abbb6fb495/05-output/qa-full.png`
- 岗位详情可运行页面：`.mastergo2html/jobs/257b5c1e-43f1-4617-81c4-21abbb6fb495/05-output/index.html`
- 校招资讯可运行页面：`.mastergo2html/jobs/2084dcbe-b524-47dc-a21b-1d6998d6edec/05-output/index.html`
- 联系我们可运行页面：`.mastergo2html/jobs/ce773f00-f2fa-4812-9d35-57aea26df634/05-output/index.html`

注意：岗位详情案例目前能看出若干真实差异，例如正文排版密度、内容区高度、按钮位置、页尾图标和部分细节还原不完全。现场可以主动指出，这正好用于说明“已有能力”和“仍需迭代”的边界。

## 三、推荐现场流程

### 1. 开场与背景，3 分钟

可直接讲：

> 今天主要想用一个真实页面，给大家看一下我们从 MasterGo 设计稿到 HTML 初稿的完整过程。我们做这个插件的背景，不是单纯希望把画面截图翻译成代码，而是想减少设计交接里的信息损失。
>
> 设计稿里有节点结构、文本、颜色、字体、图片和布局；但真正开发还需要理解模块关系、资源用途、交互状态和响应式规则。直接复制设计工具给出的绝对定位代码，视觉可能接近，但通常不利于维护。只看截图生成，又容易丢失文本、素材和层级信息。
>
> 所以我们的思路是：先由插件采集设计事实，再由本地工作流分别分析布局、组件、静态资源和交互，最后生成可运行的 HTML/CSS/JS 初稿，并保留中间产物供开发检查。

一句话定位：

> 它解决的是“从设计交付到前端第一版”的提效问题，目标是减少重复量尺寸、整理素材和搭首版页面的工作，不是替代开发完成所有业务接入。

### 2. 了解客户当前交接流程，5-8 分钟

过渡话术：

> 在演示之前，我想先了解一下你们现在真实的交接方式。这样等会儿看结果时，我们可以直接判断它对哪一段最有价值，而不是只看页面像不像。

优先问以下问题，不必全部问完：

1. 一张设计稿从设计完成到开发开始，中间会经过哪些角色和步骤？
2. 目前主要通过什么交接：标注、切图、链接、文档，还是设计师口头补充？
3. 开发拿到设计稿后，最先要补做的三件事是什么？
4. 哪类信息最容易漏：素材、字体、间距、响应式、交互状态，还是业务规则？
5. 哪些页面或模块返工最多？返工一般是视觉偏差、理解偏差，还是需求变化？
6. 设计验收现在怎么做？由谁验收，通常要来回几轮？
7. 一个常规页面从交接到首版大约需要多久？其中纯还原工作占多少？
8. 你们当前使用什么前端技术栈、组件库和设计系统？
9. PC 和移动端是分别出稿，还是由开发根据 PC 稿自行适配？
10. 如果这类工具只能先解决一个问题，你们更希望它优先解决“更像”“更快”“更可维护”还是“素材交付更完整”？

建议追问一个具体事件：

> 最近一次让你印象比较深的交接问题是什么？当时哪一步出了问题，最后花了多少时间处理？

记录四项即可：当前流程、最大痛点、可量化耗时、客户最看重的验收标准。后续介绍优势时直接对应这四项。

### 3. 介绍使用流程并启动现场任务，4-5 分钟

边操作边讲：

1. 确认插件显示“本地 MCP 在线”。
2. 在 MasterGo 中选中一个完整页面 Frame。
3. 点击“一键生成 HTML”。
4. 展示插件采集进度和任务提交状态。
5. 打开任务面板，展示当前阶段、进度、耗时、日志和中间产物。

可直接讲：

> 用户侧的主要操作只有两步：选中完整页面 Frame，然后点击一键生成。插件会采集节点树、可见文本、样式、页面截图和需要的静态资源，再把任务交给本地服务。
>
> 后面的工作不是一次模型调用。系统会依次做输入标准化、布局分析、组件结构分析、静态资源分析、交互分析、页面组装和代码生成，最后做静态校验并打包。任务即使离开插件界面也由本地服务继续执行，过程和产物可以追踪。

不要在现场承诺固定分钟数。建议说：

> 近期中等复杂度样例大多在 10-20 分钟，复杂页面、模型重试或网络波动时会更久。我们现在也把生成耗时作为明确要继续优化的问题。

## 四、等待生成时怎么讲

### 4. 先展示竞品效果，4-5 分钟

先声明比较原则：

> 我们先看一下同类方案的结果。这里不想简单判断谁好谁坏，因为不同产品优化目标不同。我们统一从设计还原、代码可维护性、素材完整性、交互和交付完整度几个维度看。

竞品展示必须尽量满足：同一设计稿、同一视口、同一素材条件、同一生成轮次。没有同条件数据时，明确说“仅用于观察能力方向，不作为严格横评”。

每个竞品只讲 1-2 分钟，按以下顺序：

1. 先展示设计图，再展示生成页，不先下结论。
2. 看整体结构：模块顺序、容器宽度、主要层级是否正确。
3. 看明显视觉：字体、图片、间距、复杂装饰和页尾。
4. 操作交互：按钮、筛选、展开、跳转或响应式。
5. 最后看代码：是否大量绝对定位、文本是否可编辑、资源是否可追踪、是否容易接入项目。

建议口径：

> 竞品在某些局部效果上可能更成熟，我们会如实参考。但对企业交付来说，除了第一眼视觉，还要看代码能不能继续维护、素材和文字有没有丢失、错误能不能定位，以及输出能不能进入现有研发流程。

不要使用“竞品做不到”“完全还原”“碾压”等无法证明的表述。

### 5. 展示本插件历史案例及设计对比，5-7 分钟

展示顺序：设计图 -> 生成截图 -> 可运行页面 -> 简看代码和产物目录。

先讲做得好的部分：

- 页面整体模块、主视觉层级和主要色彩能被识别。
- 设计稿可见文本按源节点保留，降低 AI 擅自改写文案的风险。
- 图片、SVG、复杂组合切片和来源节点有资源清单可追踪。
- 输出是本地 HTML/CSS/JS 和资源目录，可以直接打开，也可以继续改造。
- 每个 AI 阶段保留计划、耗时、token、错误和产物，失败可定位、部分阶段可重试。

再主动指出差异：

> 这里也能看到当前不足：部分字号和行距还有偏差，内容区高度与按钮位置没有完全对齐，页尾小图标出现了资源或渲染差异。这些不会回避。我们把它定位为开发初稿，下一步仍需要视觉复核和工程接入。

设计对比时不要只用“像不像”，固定看六项：

| 维度 | 现场检查内容 |
| --- | --- |
| 页面结构 | 模块顺序、容器、对齐、层级 |
| 视觉还原 | 字体、颜色、间距、圆角、背景和复杂效果 |
| 内容正确 | 文案是否遗漏或被改写 |
| 资源完整 | Logo、图片、SVG、蒙版和字体是否正确 |
| 交互行为 | 可点击、切换、展开、状态反馈 |
| 工程可用 | DOM 语义、CSS 组织、文件完整、是否便于继续开发 |

### 6. 介绍优势和当前不足，4-6 分钟

建议先把客户刚才的痛点复述出来：

> 刚才您提到现在主要耗时在【客户原话】，容易返工的是【客户原话】。结合这个流程，我们目前最直接的价值在以下几处。

当前优势：

1. 入口靠近设计现场：直接从 MasterGo 当前 Frame 发起，减少人工整理结构和素材。
2. 输入证据更完整：同时使用节点结构、原始文字、样式、资源清单和页面截图，而不只看一张图。
3. 分阶段分析：布局、组件、资源、交互和组装分开处理，减少一次生成里相互干扰。
4. 结果可追踪：保留源节点 ID、中间计划、日志、耗时和错误，便于人工检查和失败重试。
5. 交付物完整：输出原生 HTML/CSS/JS、资源目录和 ZIP，可直接预览并继续开发。
6. 可控部署：任务和文件在客户电脑的本地服务中处理；设计数据仍会按配置发送到指定模型服务，这一点需要根据客户的数据合规要求确认。

当前不足：

1. 目前主要聚焦单个完整 Frame 和单页静态页面，不是完整多页面工程生成。
2. 本地服务仍需提前启动和配置模型，普通用户的首次使用门槛偏高。
3. 近期中等复杂度页面通常需要约 10-20 分钟，复杂页面和模型重试会更久。
4. PC/移动端多 Frame 配对和真正的响应式规则仍在完善，不能只靠一张 PC 稿承诺完整移动适配。
5. 设计稿没有表达的后台接口、业务规则、异常态和复杂动效，只能保守实现或等待人工补充。
6. 蒙版、复杂透明叠加、特殊字体和缺失资源仍可能造成视觉偏差。
7. 当前已有静态代码校验，但自动截图差异检测和闭环修正还不是稳定的完整能力，视觉对比仍需要人工参与。
8. 产物应作为开发初稿，仍需进行业务接入、可访问性、兼容性、性能和安全检查。

收束口径：

> 因此我们更希望先选一类高频、结构相对稳定、视觉还原工作量大的页面做试点，用真实数据看首版耗时、返工轮次和最终可用代码比例，而不是先承诺覆盖所有页面。

### 7. 如果任务还没有完成，继续聊什么，3-8 分钟

不要连续盯着进度条。根据客户角色选一个话题深入：

设计负责人：

- 你们是否有统一图层命名、自动布局和组件规范？
- 哪些效果必须像素级一致，哪些允许工程化调整？
- 设计师是否愿意补充响应式、交互态和极端数据说明？

前端负责人：

- 现有技术栈、组件库、CSS 方案和目录规范是什么？
- 更希望拿到原生 HTML 初稿，还是直接生成 React/Vue 组件？
- 哪些代码质量门槛必须满足才能进入仓库？

项目或业务负责人：

- 当前最关心交付周期、成本、视觉一致性，还是需求变更响应速度？
- 哪类页面数量最多、重复度最高、最适合先试点？
- 如何定义试点成功：节省多少时间、减少几轮返工，还是达到多少还原度？

可以让客户当场排序：

> 如果把“生成速度、视觉还原、代码可维护、交互完整、接入现有工程”排个优先级，您会怎么排？

最后问开放问题：

> 看完现在的流程和效果，您最想先改的一点是什么？有没有哪个场景是您觉得我们还没有覆盖，但对你们特别关键的？

## 五、任务完成后的收尾，3-5 分钟

任务完成后立即回到本次现场生成结果：

1. 刷新任务状态，展示完成时间和各阶段。
2. 打开生成页面，先看首屏，再滚动查看完整页面。
3. 操作至少一个可见交互。
4. 打开输出目录，展示 `index.html`、`styles.css`、`script.js` 和 `assets/`。
5. 回到设计稿，指出一处还原较好的地方和一处仍需调整的地方。

可直接讲：

> 这就是从刚才选中的 Frame 现场生成的结果。我们既看它完成了什么，也看它还差什么。真正试点时，我们建议记录设计稿到首版的耗时、人工修改时间、验收轮次和最终可复用代码比例，用这些指标判断价值。

最后确认三件事：

1. 客户认为最有价值的环节是什么。
2. 客户最不能接受的差异是什么。
3. 是否能选 3-5 个真实页面做小范围试点，以及试点验收指标是什么。

## 六、现场应变

### 生成提前完成

不要马上打断竞品和案例讲解。完成当前小节后说：

> 刚才的任务已经完成了，我们现在回来看现场结果，并用刚才同一套六项标准检查。

### 生成长时间未完成

不要反复解释或归因。先展示任务仍在运行的具体阶段，再说：

> 当前还在【阶段名称】，说明任务没有丢失。为了不占用大家时间，我们先继续讨论试点场景。演示结束前如果仍未完成，我会用预跑结果完成后半段，同时保留本次任务日志复盘具体耗时。

### 现场生成失败

1. 展示可见错误和失败阶段，不现场长时间改代码。
2. 如果支持该阶段重试，只做一次重试。
3. 立即切换到同一 Frame 的预跑结果，保证演示完整。
4. 如实说明这也是保留中间产物和阶段日志的原因。

推荐话术：

> 这次在【阶段名称】失败了。我们先保留现场日志，不在客户时间里排查。下面用同一页面的预跑结果继续，同时把这次失败作为稳定性样本复盘。

## 七、一页提词卡

1. 背景：设计到开发存在结构、素材、状态和响应式信息损失。
2. 提问：客户当前流程、最大痛点、耗时、返工和验收标准。
3. 操作：选 Frame -> 一键生成 -> 看任务面板。
4. 等待：竞品结果 -> 自有案例 -> 设计对比。
5. 价值：更完整的设计证据、分阶段分析、可追踪、可交付。
6. 边界：单页初稿、需要本地服务、耗时、复杂效果和业务接入仍需人工。
7. 互动：客户优先级、不能接受的差异、最适合试点的页面。
8. 收尾：看现场结果，确定 3-5 个试点页面和量化指标。
