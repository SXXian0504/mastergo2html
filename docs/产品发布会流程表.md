# MasterGo2Code 产品发布会流程表

> 当前版本：Codex Skill 单路径  
> 正式发布：约 25 分钟  
> Q&A：约 5 分钟  
> 总时长：不超过 30 分钟

## 总体故事

```text
设计师的困境
→ 现有方法为什么还不够
→ 问题的本质不是模型能力
→ 将专业转换方法固化为 Codex Skill
→ 一句话触发完整工作流
→ 用剪辑视频证明产品能力
→ 用真实案例和工程结果建立可信度
→ 明确个人贡献、产品边界与未来
```

## 发布会流程表

| 篇章 | 小节 | 建议时长 | 内容 | 展示 | 备注 |
|---|---|---:|---|---|---|
| **开篇：为什么要做** | 开场命题 | 0:30 | 提出核心矛盾：设计师为了把设计稿变成页面，反而需要先学习如何写 Prompt | 纯黑背景，一句大字：**“设计师不该为了生成页面，先学会写 Prompt。”** | 不放产品名，不自我介绍，不先讲项目背景；先制造共鸣 |
|  | 困境介绍 | 0:50 | 设计师需要补充页面结构、素材、字体、布局、响应式、交互、多页面关系等大量信息 | 一句需求逐渐膨胀成多段 Prompt 的视觉动画 | 不要展示真实长 Prompt 全文，只表现“解释成本越来越高” |
|  | 现有解决方法 | 1:00 | 三类方式：人工交付给前端、现有自动转换工具、通用 Codex/Agent + MCP | 三条极简路径并列 | 只讲事实和取舍，不要变成竞品批判 |
|  | 现有方法的缺点 | 1:10 | 人工开发耗时；自动工具复杂素材和布局容易偏差；通用 Agent 灵活但依赖长 Prompt、反复补充上下文 | 页尾 Logo 黑框、布局错位等真实结果，大面积局部特写 | 用相同设计稿、相同位置对比；这是第一个视觉证据 |
|  | 开发动机 | 0:30 | 开发目标不是再做一个代码生成器，而是让设计师不必每次重新发明转换工作流 | 黑底大字：**“不要让用户记住方法，让 Skill 记住方法。”** | 从困境转向解决方向 |
| **洞察：重新定义问题** | 问题重构 | 0:40 | 问题不是模型不会写代码 | 黑底大字：**“问题不是模型不会写代码。”** | 说完停顿约 1 秒，再翻页 |
|  | 核心洞察 | 0:40 | 真正的问题是设计事实、执行步骤和验收规则没有进入一个稳定流程 | 黑底大字：**“而是正确的方法，没有被固化。”** | 这是整场最重要的故事转折之一 |
|  | 解决原则 | 1:00 | 三项原则：读取完整设计事实；逐页生成和验证；最后再进入 React 工程 | 三个短语依次出现：**Read Design / Verify Every Page / Build the Project** | 不展开内部十几个技术阶段 |
| **产品登场：一种更简单的方式** | 产品 Reveal | 0:45 | 正式发布产品：MasterGo2Code，作为 Design-to-React Codex Skill | 纯黑背景，产品名使用一次 Mask Reveal | 全场最明显的一次 Slide 动效只放这里 |
|  | 一句话指令 | 0:45 | 用户只需要输入：“将当前选中的 MasterGo 页面转换成 React 项目。” | 暖白背景，真实指令居中，下方小字 **That’s it.** | 这是整场第二张最值得被记住的页面 |
|  | Skill 的职责 | 1:10 | Skill 自动接管读取设计、逐页生成、视觉验证、React 合并和工程检查 | 五阶段横向流程：**读取设计 → 逐页生成 → 视觉验证 → React 合并 → 工程检查** | 强调“Skill 固化专业方法”，不是“Skill 等于一段 Prompt” |
| **实操：让结果说话** | Demo 章节过渡 | 0:15 | 从概念进入完整实操 | 黑底大字：**“From frames to a working product.”** | 停顿后播放视频 |
|  | 剪辑实操视频 | 4:30 | 展示多个 MasterGo Frame；Codex 一句话指令；Skill 加载；逐页生成；截图验证；React 合并；路由跳转；响应式；工程验证 | 全屏 16:9 剪辑视频 | 不做现场操作；播放前提醒观众关注“输入多少信息”和“Skill 接管多少步骤” |
|  | Demo 结论 | 0:25 | 总结：用户只描述目标，Skill 负责专业过程 | 视频最终画面定格，叠加一句：**“One instruction. One working project.”** | 不立刻进入技术细节，先让结果停留 |
| **证明：为什么这个结果可信** | 复杂素材 | 0:55 | 重点展示蒙版 Logo、SVG、装饰素材等没有变成黑框或占位元素 | 设计稿 / 普通结果 / MasterGo2Code 三方局部对比 | 标题只写：**“复杂素材，完整保留。”** |
|  | 布局还原 | 0:55 | 展示页面主要区域、间距、对齐和内容层级基本保持 | 设计稿与生成结果叠加切换，或左右滑动对比 | 不承诺所有页面 100% 像素级还原 |
|  | 多页面工程 | 1:00 | 每个 Frame 独立生成和验证，再合并为一个具有真实路由的 React / Next.js 项目 | 三个页面卡片收拢为一个浏览器/工程窗口 | 标题：**“多个页面，一个工程。”** |
|  | 工程可用性 | 1:00 | 展示路由跳转、TypeScript、Production Build、视觉验证等结果 | 浏览器为主，右下角只显示 3 个绿色状态标签 | 不长时间展示终端；工程结果作为产品可信度证据 |
| **价值：它改变了什么** | Before / After | 1:10 | Before：长 Prompt、重复解释、逐页人工整理；After：一句目标、固定工作流、可继续开发的工程 | 左右两种工作方式极简对比 | 不要比较功能数量，比较用户需要承担的工作 |
|  | 用户价值 | 0:50 | 对设计师：减少解释和交付损失；对前端：从可运行首版开始；对团队：工作流可重复 | 三句话逐页或依次出现 | 如果页面太拥挤，可以拆成两页快速讲 |
| **幕后：为什么是我做的** | 个人贡献 | 1:20 | 项目由个人独立完成：设计采集、素材处理、AI 工作流、HTML 生成、视觉验证、React 迁移、工程检查 | 黑底大字：**“One workflow. Built end-to-end.”**，下方一条闭环 | 不做实习周报式任务清单；重点体现问题定义、系统设计和落地能力 |
| **未来：它现在在哪里** | 产品边界 | 0:50 | 当前解决的是“设计交付到可运行首版”；复杂业务逻辑、接口和特殊效果仍需要开发处理 | 暖白背景大字：**“第一版，不是终点。”** | 主动说清边界会增强可信度 |
|  | 下一步 | 0:50 | 标准测试集、Token/成本统计、复杂交互、团队组件库接入、自动视觉修正 | 一条由现在延伸到未来的细线或三个阶段 | 最多三个方向，不讲完整 Roadmap |
| **收尾：回到唯一主张** | 价值回扣 | 0:40 | 它不是另一个大 Prompt，而是把设计稿转代码的专业方法交给 Skill | 黑底，产品名逐渐出现 | 回扣开场“设计师不应该学 Prompt” |
|  | Closing | 0:30 | 最终 Slogan：一句话，从设计稿到 React 项目 | **MasterGo2Code** + **“一句话，从设计稿到 React 项目。”** | 画面停留两秒，再口头说“谢谢” |
| **Q&A** | 评审问答 | 5:00 | 回答技术原理、视觉指标、成本、边界、个人贡献和未来规划 | 根据问题切换备用页 | 准备备用页，不把全部细节塞入主发布流程 |

正式内容目标约 24 分钟，预留约 5 分钟 Q&A 和接近 1 分钟的设备、翻页或临时缓冲。第一次排练如果超过 25 分钟，继续按照下方优先级删减。

## 建议删减优先级

如果第一次排练超过 25 分钟，按以下顺序删减：

1. 将“现有解决方法”和“缺点”合并；
2. 用户价值从三类用户缩减为设计师与前端两类；
3. 下一步只保留两个方向；
4. 工程验证只展示状态，不解释实现过程；
5. Demo 视频从 4:40 缩短到 4:00；
6. 不删开场、问题重构、产品 Reveal、真实视频、Hero Case 和结尾。

## 主流程必须保留的六个记忆点

1. **设计师不该为了生成页面，先学会写 Prompt。**
2. **问题不是模型不会写代码，而是正确的方法没有被固化。**
3. **MasterGo2Code 是一个 Design-to-React Codex Skill。**
4. **用户只需要输入一句目标。**
5. **多个设计页面最终成为一个可运行 React 项目。**
6. **一句话，从设计稿到 React 项目。**
