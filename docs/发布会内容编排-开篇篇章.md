## 一、开篇篇章的任务

开篇不急于介绍产品，也不先讲技术架构。它只完成三件事：

1. 让设计师观众对“设计稿转代码时的解释成本”产生共鸣；
2. 用同一个设计稿、同一组观察点，展示现有方式的真实偏差；
3. 将问题从“模型不够聪明”转向“专业转换方法没有被固化”，自然引出后续产品动机。

### 开篇主张

> **设计师不该为了生成页面，先学会写 Prompt。**

### 开篇结束时观众应该记住的结论

> 现有工具可以生成代码，但还没有稳定地理解设计稿；我们需要的是一套轻量、可控、精准、可验证的转换方法。

## 三、统一视觉与演示规范

### 3.1 画面基调

- 画面比例：16:9，建议基准画布 1920 × 1080。
- 开篇主色：黑色 `#0A0A0A`、暖白 `#F5F3EF`、警示红 `#FF4D4F`。
- 黑色用于提出问题，暖白用于展示事实，红色只用于圈出偏差，不作为装饰色。
- 页面文字尽量只保留一个结论；技术名词放在页脚或旁注，不抢主叙事。
- 动效采用“出现—放大—停留—收束”的节奏，不使用持续旋转、无意义漂浮和密集粒子。

### 3.2 现场对比的公平条件

两种方式必须使用：

- 同一个 MasterGo 页面；
- 同一个目标视口；
- 同一组素材和字体条件；
- 同一组重点观察区域；
- 截图或录屏前不进行人工修图。

页面页脚固定显示：

> Same design input · Same viewport · First generated result

这句话用于说明展示的是可观察结果，不是对工具的主观评价。

### 3.3 开篇不展示的内容

- 不展示长 Prompt 全文，避免观众陷入阅读代码；
- 不在此处展示完整内部架构、脚本和中间 JSON；
- 不在开篇宣称具体还原度百分比；
- 不把问题归因成某个工具“完全不可用”；
- 不提前解释产品的全部能力，把解决方案留到下一篇章。

# 四、小节一：困境介绍

## 4.1 叙事定位

**一句话结论：** AI 会写代码，但设计师仍要花大量时间解释“这个设计到底是什么”。

**观众情绪：** 从熟悉、轻微无奈，到意识到问题并不只是工具操作复杂。

**本节结束动作：** 大段 Prompt 停止增长，画面切黑，留下“代码生成了，设计却不一定被理解”的过渡语气。

## 4.2 画面内容设计

### HTML 场景 A｜一句话需求

黑色背景，中央只有一行文字：

```text
把这个 MasterGo 页面转换成 HTML
```

文字下方不放按钮，只放一条极细的灰色输入线，模拟设计师向工具提出目标。

### HTML 场景 B｜隐含信息逐项浮现

输入线下方依次出现 6 个信息标签：

```text
页面结构    素材与蒙版    字体与样式
布局关系    响应式       交互与页面关系
```

每个标签先以低对比度出现，随后连接到“Prompt”字样。标签之间出现细线，表示这些信息不是独立的，而是彼此关联。

### HTML 场景 C｜Prompt 膨胀

中央输入框从一行变成多行，内容不需要展示真实长 Prompt，可采用可读的抽象片段：

```text
请保留原设计中的页面层级……
请确保页尾 Logo 使用正确素材……
请处理图片与蒙版关系……
请不要使用固定画布……
请补充响应式布局……
请恢复页面跳转和交互状态……
```

最后一行被推到画面底部，出现小字：

> 用户表达的是目标，实际承担的却是方法说明、上下文补充和结果验收。

## 4.3 动效时间轴

| 时间 | 动效 | 画面状态 |
|---:|---|---|
| 0.00–0.08 | 淡入 | 黑底，中央一句需求 |
| 0.08–0.18 | 轻微光标闪烁 | 模拟输入完成，不播放打字音效 |
| 0.18–0.34 | 依次上浮 | 6 个隐含信息标签按“结构—素材—布局—响应式—交互”顺序出现 |
| 0.34–0.48 | 高度增长 | 输入框由 1 行扩展为 5–6 行，标签连接线逐渐变亮 |
| 0.48–0.58 | 停留 | 大字结论：**一句话的需求，常常变成几十行解释。** |
| 0.58–0.65 | 收束 | 所有标签和输入框缩成一条细线，准备切入现有方法 |

> 动效时长可按录音微调；若采用幻灯片播放，建议将 0.18–0.48 的标签出现与 Prompt 增长做成可逐步控制的分段，而不是一次性播放。

## 4.4 主持/演讲稿

> 今天，AI 已经很会写代码了。
>
> 但当设计师真正想把一个 MasterGo 页面变成网页时，第一步往往不是点击“生成”，而是开始解释。
>
> 这个页面有哪些层级，哪些是组件，哪些是素材；图片和蒙版是什么关系；字体、颜色、间距应该怎么保留；不同屏幕尺寸怎么适配；点击之后要不要跳转到另一个页面。
>
> 这些信息少说一项，结果就可能偏一截。
>
> 于是，一句“把这个页面转换成 HTML”，慢慢变成一大段 Prompt，再变成一轮一轮的补充和修改。
>
> **设计师并没有因此更接近结果，反而被迫先学会怎么指挥 AI。**

## 4.5 切入下一小节的话术

> 那么，如果我们把同一个设计稿交给目前常用的两条路径，结果到底会有什么不同？我们不先讨论模型能力，直接看生成结果。

# 五、小节二：现有方法、缺点

## 5.1 叙事定位

**一句话结论：** 两条路径各有优势，但在复杂素材、布局关系和使用成本上，都把一部分工作留给了设计师。

**展示原则：** 先展示路径差异，再展示结果差异；先说优点，再说观察到的问题，避免形成主观攻击。

## 5.2 第一屏：两条路径

### HTML 场景 D｜路径对照

画面暖白，左右两列：

**左列：Codify 插件**

```text
选中 Frame
   ↓
调用插件
   ↓
获得 HTML
```

标签：

- 操作直接
- 上手成本低
- 适合快速尝试

**右列：Codex + 官方 MCP**

```text
选中 Frame
   ↓
编写 Prompt
   ↓
补充上下文
   ↓
反复修正
   ↓
获得 HTML
```

标签：

- 更灵活
- 可补充更多要求
- 结果依赖指令质量

底部统一提示：

> 两条路径的共同问题：设计稿事实、结果验证和工程化约束没有被稳定固化。

## 5.3 第二屏：相同设计稿、相同观察点

### HTML 场景 E｜输入条件锁定

屏幕左侧放原始设计稿的完整缩略图，右侧放 3 个观察点卡片：

1. 页尾 Logo / 蒙版素材；
2. 主内容区的横向布局与间距；
3. 图片、字体和颜色的实际表现。

顶部标题：

> 同一个设计稿，我们只看第一次生成结果。

动画先让设计稿出现，再让 3 个观察点以编号 ①②③ 的形式落位。点击后进入左右结果对比。

## 5.4 第三屏：Codify 结果

### 重点展示问题

根据《D2C现状调研》中的真实现象，优先展示三处，不一次展示所有问题：

- **蒙版素材异常：** 原设计中的图片/蒙版关系没有被完整保留；
- **页尾 Logo 变成黑框：** 观众一眼可以识别“资源或渲染结果不对”；
- **布局错位：** 页面主体的相对关系发生变化，局部位置偏移。

右侧或下方使用小字说明：

> 观察到的现象：资源、层级与布局关系没有完整进入生成结果。

不要使用“失败”“不可用”等绝对表述，除非展示素材确实达到不可用程度。

## 5.5 第四屏：Codex + 官方 MCP 结果

### 重点展示问题

- 结果可以通过 Prompt 继续调整，灵活性更高；
- 但初始阶段需要较长 Prompt；
- 一旦上下文遗漏，仍可能出现素材、布局或样式偏差；
- 多轮补充会增加时间成本、沟通成本和 Token 消耗。

画面建议：

- 左侧显示结果页面；
- 右侧用半透明叠层显示“第 1 次指令 / 补充素材 / 修复布局 / 再次生成”的时间线；
- 不展示大段真实 Prompt，只显示每轮补充的意图。

## 5.6 结果对比动效设计

| 阶段 | 动效 | 目的 |
|---|---|---|
| 1 | 两条路径卡片同时亮起 | 说明两种方式都被公平展示 |
| 2 | 原始设计稿从中间展开为全屏 | 锁定相同输入 |
| 3 | 设计稿向左右分裂，分别进入两种生成路径 | 建立可比关系 |
| 4 | 左右结果同时出现 | 避免先展示某一方造成预设立场 |
| 5 | 画面中心出现扫描线，从上到下扫过 | 模拟视觉验收，不使用夸张特效 |
| 6 | 页尾 Logo 区域放大到 180%–220% | 第一处证据：黑框/素材异常 |
| 7 | 主体布局区域出现细红框和轻微位移标记 | 第二处证据：布局错位 |
| 8 | 蒙版区域做一次左右擦除对比 | 第三处证据：蒙版关系异常 |
| 9 | 红框退场，保留三处编号 | 从“指出问题”转向“归纳问题” |
| 10 | 两条路径退到背景，中央浮现结论 | 进入开发动机 |

### 对比页的结论文案

> 不是“有没有生成代码”的问题，
> 而是“设计意图有没有被完整保留”的问题。

## 5.7 演讲稿

> 现在看两种常见方式。
>
> 第一种是直接使用 Codify 插件。它的优点很明确：操作直接，设计师不需要组织很长的指令，很快就能拿到一个 HTML 结果。
>
> 第二种是使用 Codex 加官方 MCP。它更灵活，我们可以继续补充素材、布局、响应式和交互要求；但相应地，也需要更长的 Prompt、更完整的上下文，以及多轮修正。
>
> 我们用同一个设计稿、同一个视口，直接看第一次生成的结果。
>
> 在 Codify 的结果里，页尾 Logo 出现了黑框，蒙版素材没有按原设计呈现，主体布局也发生了错位。这些都不是代码有没有生成的问题，而是设计稿里的资源关系和布局关系没有被完整理解。
>
> Codex 加官方 MCP 的结果更灵活，但它把一部分专业工作转移给了使用者：你需要不断解释、补充和验收。只要上下文不完整，结果仍然会偏；而每一次补充，也意味着更多时间和 Token 消耗。
>
> 所以，现有方式并不是没有价值。它们分别解决了“快速得到结果”和“灵活调整结果”，但还没有稳定解决“如何把设计意图完整地带到代码里”。

## 5.8 本节收束话术

> 当设计师需要自己记住每一个转换步骤、每一个验收条件时，工具的智能就还没有真正沉淀下来。
>
> 我们开始思考：能不能把这套方法本身固化下来？

# 六、小节三：开发动机

## 6.1 叙事定位

**一句话结论：** 不要让用户每次重新组织方法，让 Skill 记住经过验证的专业流程。

这页是开篇的转折页，不展开产品架构，不承诺“一键上线”，只说明为什么要做。

## 6.2 HTML 场景 F｜方法被固化

黑色背景，刚才对比页中的 6 个标签、3 个问题编号和两条路径逐渐汇聚到中央一个圆角容器：

```text
DESIGN-TO-CODE METHOD
```

容器下方依次出现 4 个小词：

```text
读取设计事实  →  理解结构  →  生成页面  →  验证结果
```

最后切换为中文主张：

> **不要让用户记住方法，让 Skill 记住方法。**

页脚小字：

> 更快验证设计稿的实际呈现效果，减少设计交付中的反复沟通与手动还原。

## 6.3 动效时间轴

| 时间 | 动效 | 画面状态 |
|---:|---|---|
| 0.00–0.12 | 问题标签回收 | “素材 / 布局 / Prompt / 验收”等碎片从四周向中心移动 |
| 0.12–0.22 | 容器成形 | 中央容器由一条线扩展为圆角矩形 |
| 0.22–0.36 | 四阶段逐个点亮 | 读取设计事实、理解结构、生成页面、验证结果 |
| 0.36–0.48 | 主张出现 | 中文主张淡入，其他元素降低对比度 |
| 0.48–0.58 | 停留 | 保留至少 0.8 秒，给主持人完成转折 |
| 0.58–0.65 | 出场 | 中央容器缩小到右上角，接入下一篇章的产品 Reveal |

## 6.4 演讲稿

> 这让我们重新定义了问题。
>
> 我们不是再做一个“帮用户写代码”的工具，也不是要求每一个设计师都变成 Prompt 工程师。
>
> 我们真正想做的是，把设计稿转换中已经验证过的方法、步骤和验收规则固化下来。
>
> 让系统去读取设计事实，理解页面结构，处理素材和布局，生成页面，再用视觉结果验证它。
>
> **不要让用户记住方法，让 Skill 记住方法。**
>
> 这样，设计师只需要更快地验证设计稿在真实网页中的呈现效果；设计和开发之间，也少一轮解释，少一轮手动还原。

## 6.5 进入下一篇章的话术

> 接下来，我们不再只看问题，而是看这套方法如何真正工作：从设计稿出发，如何一步一步走到一个可运行、可验证、可继续开发的项目。

# 七、开篇 HTML 展示页的实现规格

以下内容用于后续实现 3 个独立场景或一个可控演示页面。建议先实现成单页 `opening-demo.html`，通过键盘或按钮控制场景，发布会正式版再录制成视频。

## 7.1 场景状态

```text
opening/01-request
opening/02-context-expansion
opening/03-two-paths
opening/04-same-input
opening/05-codify-result
opening/06-codex-result
opening/07-method-solidified
```

建议支持：

- `Space`：进入下一场景；
- `ArrowLeft / ArrowRight`：前后切场景；
- `R`：当前场景重播动效；
- `F`：进入/退出演示全屏；
- 屏幕右下角提供极简进度点，录屏时可隐藏。

## 7.2 组件分层

```text
DemoStage
├── SceneBackground
├── SceneTitle
├── PromptGrowth
├── PathComparison
├── DesignReference
├── ResultComparison
├── FocusZoom
├── ConclusionStatement
└── SceneProgress
```

## 7.3 动效实现约束

- 优先使用 CSS transform、opacity、clip-path，避免逐帧改变大量布局属性；
- Prompt 膨胀使用高度和 `clip-path`，不要让真实长文本在录屏时产生滚动抖动；
- 对比页面的放大裁切使用同一张结果图的 `transform: scale()`，保持像素关系稳定；
- 所有动效提供 `prefers-reduced-motion` 降级，降级后仍保留顺序和结论；
- 不依赖网络字体和远程图片；正式录屏前将素材打包到本地 `assets/`；
- 不使用浏览器默认滚动条作为演示重点；
- 录制视口固定为 1920 × 1080，避免窗口变化造成对比误差。

## 7.4 需要准备的素材

| 素材 | 用途 | 要求 |
|---|---|---|
| 原始 MasterGo Frame 截图 | 相同输入条件 | 与实际演示视口一致 |
| Codify 首次生成结果截图 | 现有方法对比 | 保留 Logo、蒙版和布局问题 |
| Codex + 官方 MCP 首次结果截图 | 现有方法对比 | 保留真实 Prompt 轮次信息，但不展示敏感内容 |
| Logo 局部裁切图 | 重点放大 | 三种结果使用同一裁切范围 |
| 蒙版局部裁切图 | 重点放大 | 统一缩放比例和背景 |
| 主体布局局部裁切图 | 重点放大 | 标出基准线和错位方向 |
| 演示字体 | 所有页面 | 本地化，避免现场字体替换 |

# 八、现场执行清单

## 8.1 演讲前

- [ ] 锁定最终对比 Frame 与视口；
- [ ] 确认三处问题在同一版本结果中可见；
- [ ] 将原设计稿、两种结果、三处局部特写统一命名；
- [ ] 检查 Logo、蒙版、图片在演示机器上不会因路径失效；
- [ ] 将演示页面设置为离线可运行；
- [ ] 预录一份完整开篇视频，并保留静态截图兜底；
- [ ] 为每个场景准备“下一页”与“重播”快捷键；
- [ ] 讲稿中的“第一次生成结果”与素材版本一致。

## 8.2 现场播控

1. 开场保持黑屏 1 秒，再进入“一句话需求”；
2. 困境介绍不点击暂停，保证情绪连续；
3. 路径对比时先展示两种方式的优点，再展示结果偏差；
4. 放大 Logo 和布局时停留 1 秒，给观众建立视觉记忆；
5. 不在问题页现场修代码；若素材异常，切换预录视频或静态截图；
6. 开发动机页至少停留 1 秒，再进入产品 Reveal。

> 这里展示的是第一次生成结果。重点不是证明某一次结果一定失败，而是说明不同路径承担了多少解释、补充和验收工作。

# 九、后续篇章的编排模板

后续每个篇章继续按以下字段设计：

| 字段 | 说明 |
|---|---|
| 篇章目标 | 这一段结束后，观众应该改变什么认知 |
| 小节结论 | 一屏可以记住的一句话 |
| 展示内容 | HTML 页面、录屏、截图或现场操作 |
| 动效时间轴 | 每个阶段的出现、强调、停留和出场 |
| 演讲稿 | 可直接口播的完整稿件 |
| 转场话术 | 从本节自然进入下一节的句子 |
| 现场备份 | 失败、提前完成或时间不足时的替代方案 |
| 素材清单 | 实现和录制所需的截图、页面、字体和数据 |

建议下一步按顺序继续：

1. **洞察篇章：** 从“生成代码”转向“设计到代码是一条工作流”；
2. **产品登场篇章：** 产品命名、主张和一句指令的 Reveal；
3. **实操展示篇章：** MasterGo 多 Frame 到 React 项目的完整演示；
4. **产品优势篇章：** 精确度、简单使用、工程交付三组证据；
5. **收尾与 Q&A：** 产品边界、个人贡献、下一步计划和现场问答。
