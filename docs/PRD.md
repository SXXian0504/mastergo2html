# MasterGo2JSON AI 高保真 HTML 生成需求文档

## 1. 背景

当前插件已经可以从 MasterGo 选中设计稿中导出基础数据包：

- `raw.json`：选中节点树的精简结构、绝对布局、文本、样式、图片引用等。
- `asset-manifest.json`：图片资源映射表，核心字段包括 `imageRef`、`assetId`、`copiedPath`、`sourceNodes`。
- `assets/original/*.png`：原始图片资源，可选导出。
- `assets/rendered/*.png`：节点渲染切片，可选导出。

现有导出能力解决了“拿到设计稿信息”的问题，但 `raw.json` 基本保留 MasterGo 的绝对定位语义，直接用于 HTML 开发会导致页面结构难维护、布局不自然、响应式扩展困难。下一阶段需要接入 AI 与规则化处理能力，把设计稿信息转化为适合前端开发的页面结构、模块计划、资源计划、交互计划，并最终生成高保真 HTML 页面。

同时，当前在图片较大或图片数量较多时，导出原图和渲染切片会明显变慢，用户容易感知为卡住。实测也发现，MasterGo 插件即使隐藏 UI，只要插件任务仍在运行，用户仍可能无法正常控制画布。因此在接入 AI 前，必须把导出链路拆成“插件轻量提交 + 外部任务执行 + 状态可恢复查询”的稳定流程，避免长任务驻留在插件运行态中。

## 2. 产品目标

1. 将 MasterGo 设计稿自动转化为可用于 HTML 生成的结构化中间产物。
2. 支持基于模块的 AI 分工分析：组件结构、静态资源、动态交互。
3. 支持模块整合计划生成，解决页面级布局、模块顺序、共享样式、资源引用和状态流转。
4. 生成单页高保真 HTML 页面，并可通过设计稿截图进行视觉比对与迭代。
5. 在 MasterGo 插件 GUI 中提供“一键生成 HTML”的启动入口，用户不需要手动导出 ZIP 后再运行命令。
6. 优化大图导出体验，避免插件长时间占用 MasterGo 画布控制权。
7. 支持外部面板实时查看任务进度，并支持插件重新打开后读取任务状态。
8. 保留足够清晰的中间产物，方便人工审查、二次生成、失败重试和调试。

## 3. 非目标

短期内不做以下事情：

- 不直接在 MasterGo 插件内完成所有大模型调用和代码生成。
- 不要求 MasterGo 插件在关闭后继续执行后台任务；长任务由外部 MCP/本地服务承担。
- 不把插件内隐藏 UI 或缩小窗口视为真正后台运行方案。
- 不要求 MasterGo 插件直接连接 stdio MCP；插件通过本地 HTTP/WebSocket bridge 与 MCP/本地服务通信。
- 不支持完整多页面站点工程生成，先聚焦单个选中页面或 Frame。
- 不承诺自动识别所有业务数据接口，动态交互先以静态模拟数据、筛选、展开、切换等前端行为为主。
- 不做通用设计系统抽取平台，先服务“从当前设计稿到高保真 HTML”的闭环。
- 不追求 100% 像素级还原所有复杂特效，优先保证页面结构、视觉层级、主要间距、字体、颜色、图片和关键交互。

## 4. 目标用户与使用场景

主要用户：

- 前端开发者：希望快速得到可维护的 HTML/CSS/JS 初稿。
- 设计交付人员：希望把 MasterGo 设计稿转换成可验证的网页原型。
- AI 工作流调试者：需要查看每一步中间产物，定位布局、资源或交互理解错误。

核心场景：

1. 用户在 MasterGo 中选中一个完整页面 Frame。
2. 用户在插件 GUI 中点击“一键生成 HTML”。
3. 插件检查本地 MCP/任务服务是否可用；如果不可用，提示启动服务或回退到离线 ZIP 导出。
4. 插件抓取轻量 JSON 结构、资源映射和必要静态资源，形成任务输入。
5. 插件通过本地 HTTP/WebSocket bridge 提交任务给 MCP/本地服务。
6. 插件保存 `jobId` 后调用 `closePlugin()`，把画布控制权还给用户。
7. 用户通过外部面板实时查看任务阶段、进度、日志和下载入口。
8. 用户重新打开插件时，插件读取最近 `jobId` 并展示任务状态。
9. MCP/本地服务将 `raw.json` 和资源清单转化为页面布局描述。
10. 系统按模块切片，并分别生成组件、资源、交互开发计划。
11. 系统生成模块整合计划。
12. AI 根据计划生成 HTML 页面。
13. 系统使用页面截图和设计稿截图做视觉比对，必要时迭代修正。

## 5. 总体方案

推荐采用“插件 GUI 一键启动 + 插件轻量采集提交 + MCP/本地服务执行 + 外部面板进度 + 插件重开查状态”的架构。

插件内负责：

- 提供“一键生成 HTML”的主按钮和服务状态提示。
- 检查 MCP/本地任务服务是否可用。
- 扫描选中节点。
- 导出或生成 `raw.json`、`asset-manifest.json` 等轻量任务输入。
- 默认引用图片资源，按需抓取少量关键静态资源。
- 生成资源映射表。
- 通过本地 HTTP/WebSocket bridge 提交任务到 MCP/本地服务并获取 `jobId`。
- 将最近任务的 `jobId`、提交时间、源页面和选区摘要写入 `mg.clientStorage`。
- 提交成功后调用 `mg.closePlugin()`，避免插件长时间占用画布控制权。
- 插件重新打开时查询最近任务状态，展示结果、错误或下载入口。

MCP/本地服务负责：

- 接收插件提交的任务输入。
- 对外暴露插件可访问的本地 HTTP/WebSocket bridge，例如 `POST /jobs`、`GET /jobs/:jobId`、`GET /jobs/:jobId/logs`。
- 在服务内部调用 MCP tools 或直接执行本地 workflow。
- 管理任务队列、状态、日志和产物目录。
- 标准化 `raw.json`。
- 生成页面布局中间产物。
- 进行模块识别与切片。
- 调用多个 AI 职责角色生成开发计划。
- 汇总模块整合计划。
- 生成 HTML/CSS/JS。
- 截图比对、自动修正和输出报告。
- 打包 ZIP 并提供本地下载地址或产物路径。

外部面板负责：

- 根据 `jobId` 实时轮询或订阅任务状态。
- 展示阶段、百分比、当前步骤、失败数、日志摘要和下载入口。
- 支持打开生成页面预览、查看中间产物和复制产物路径。

这样可以真正降低插件卡顿和画布不可操作风险，也能避免把模型密钥、长任务、文件系统写入、截图验证等复杂能力塞进 MasterGo 插件沙箱。

对于当前页面所有 Frame 的一键生成，默认只允许插件侧采集结构和资源引用。原图、渲染切片和大图片资源必须走按需补导流程，不能作为插件主路径的同步全量任务。

### 5.1 一键启动边界

用户体验目标是“在插件 GUI 里点一次按钮即可启动完整 HTML 生成流程”，但执行边界必须拆开：

- 插件负责点击入口、服务检查、当前选区数据采集、必要资源采集、任务提交和 `jobId` 保存。
- MCP/本地服务负责 AI 计划、HTML 生成、视觉 QA、ZIP 打包和任务状态持久化。
- 外部面板负责实时进度和最终产物下载。
- 插件关闭后不能继续调用 `mg` API，因此所有依赖 MasterGo 当前文档上下文的数据必须在提交任务前采集，或作为后续补导任务重新打开插件执行。

### 5.2 任务状态回传方案

首选组合：

- 外部面板实时进度：用于长任务运行期间查看进度、日志和下载入口。
- 插件重新打开读取状态：用于用户回到 MasterGo 后查看最近任务是否完成、失败或仍在运行。

任务状态最小字段：

- `jobId`
- `status`：`queued`、`running`、`done`、`error`、`canceled`
- `phase`：当前阶段，例如 `normalize-raw`、`layout-analysis`、`module-slicing`、`ai-planning`、`html-generation`、`visual-qa`、`package-files`
- `percent`
- `message`
- `sourcePageId`
- `selectionIds`
- `createdAt`
- `updatedAt`
- `downloadUrl` 或 `outputPath`
- `error`

插件重新打开后的行为：

- 从 `mg.clientStorage` 读取最近 `jobId`。
- 请求 MCP/本地服务的 `GET /jobs/:jobId`。
- 如果任务完成，展示摘要和下载入口。
- 如果任务仍在运行，展示当前阶段，并提供打开外部面板的入口。
- 如果服务不可用，展示本地服务未启动或任务状态不可查询的提示。

## 6. 中间产物设计

### 6.0 样例数据定位

`job-list.modules.example.json` 只能作为业务语义样例，不能作为正式 schema 的完整依据。它已经覆盖了页面模块、业务文案、导航项、筛选项、职位列表、分页、资源引用等信息，但对高保真 HTML 生成仍然不足，主要缺少：

- 视觉 token：颜色、字体族、字号、字重、行高、透明度、阴影、圆角、背景模糊、边框等。
- 布局约束：固定宽度、内容容器、模块间距、左右栏比例、卡片间距、层叠顺序、吸顶区域、缩放策略等。
- CSS 状态：hover、active、disabled、checked、indeterminate、collapsed、focus-within 等。
- 响应式策略：设计稿宽度、缩放方式、断点、最小宽度、移动端降级规则等。
- 组件实现提示：哪些节点应转成真实 DOM，哪些适合背景图，哪些可以用 CSS 绘制，哪些只是装饰。

因此正式中间产物需要拆成两层：

- 业务语义层：描述页面是什么，例如模块、文案、列表数据、筛选项、链接和交互含义。
- 视觉实现层：描述页面怎么实现，例如 CSS token、布局约束、状态样式、资源使用和响应式策略。

### 6.1 JSON 与 Markdown 取舍

JSON 适合：

- 程序读取。
- schema 校验。
- 模块切片。
- 资源映射。
- 生成代码时的确定性引用。
- 支持失败重试和增量处理。

Markdown 适合：

- AI 阅读。
- 人工审查。
- 表达布局判断、设计意图、风险提示和实现策略。
- 保存多角色开发计划。

结论：

- 结构性数据使用 JSON。
- 推理性、解释性、计划性内容使用 Markdown。
- 关键 Markdown 文件应引用对应 JSON 文件和节点 ID，避免变成不可追溯的自然语言描述。

### 6.3 核心产物说明

`raw.normalized.json`

- 对 `raw.json` 做字段清洗、单位统一、图片引用补全、节点可见性过滤。
- 保留原始 `sourceNodeId`，确保所有判断可回溯。

`page-layout.json`

- 页面级布局结构。
- 从绝对定位推导出模块顺序、容器宽度、内容区宽度、栅格、吸顶区、背景层、模块重叠关系。
- 用于程序切片和后续生成。

`page-layout.md`

- 面向 AI 和人工审查的页面布局说明。
- 描述页面从头到尾的模块、层级、布局方式、视觉重点、响应式建议。

`*.module.json`

- 单个模块的结构化切片。
- 包含模块边界、节点列表、文本、样式摘要、图片引用、布局约束、状态样式、可能的组件树。

`design-tokens.json`

- 页面级视觉 token。
- 包含颜色、字体、字号、行高、字重、圆角、阴影、边框、模糊、间距、z-index、断点等。
- 用于防止 AI 只理解业务内容而丢失 CSS 设计细节。

`asset-export-plan.json`

- 按需补导资源计划。
- 包含资源优先级、用途、来源模块、补导批次、计划型切片节点、降级策略。
- 用于避免插件一次性导出所有原图和切片。

`*.plan.md`

- 多角色 AI 输出的开发计划。
- 分为组件计划、资源计划、交互计划。
- 计划必须引用 `module.json` 中的模块 ID、节点 ID 和资产 ID。

`assembly.plan.md`

- 面向最终代码生成 AI 的整合说明。
- 描述实现优先级、容易失真的区域、截图比对关注点。

## 7. AI 职责划分

### 7.1 页面布局分析 AI

输入：

- `raw.normalized.json`
- `asset-index.json`
- `design-tokens.json`
- 页面截图，可选

输出：

- `page-layout.json`
- `page-layout.md`

职责：

- 判断页面整体结构和模块边界。
- 将绝对坐标转化为 HTML 友好的相对布局描述。
- 标记固定宽度、流式布局、居中容器、背景图、悬浮装饰、重复列表等模式。
- 提取页面级视觉约束，例如设计稿基准宽度、吸顶导航、背景层、缩放策略、模块 z-index 关系。

### 7.2 组件开发计划 AI

输入：

- 单个 `*.module.json`
- `page-layout.md`

输出：

- `*.component.plan.md`

职责：

- 设计模块内部 DOM 结构。
- 判断可复用组件。
- 将重复卡片、列表项、导航项等抽象为数据驱动结构。
- 说明 CSS 布局方式，例如 flex、grid、position、aspect-ratio。

### 7.3 静态资源计划 AI

输入：

- 单个 `*.module.json`
- `asset-manifest.json`
- `asset-index.json`

输出：

- `*.asset.plan.md`

职责：

- 判断每个图片资产的用途。
- 决定使用原图、渲染切片、CSS 绘制或忽略装饰资源。
- 给出 `assetId` 到最终 `copiedPath` 的引用方案。
- 标记缺失图片的降级策略。

### 7.4 动态交互计划 AI

输入：

- 单个 `*.module.json`
- 页面业务语义说明，可选

输出：

- `*.interaction.plan.md`

职责：

- 识别搜索、筛选、tab、展开收起、轮播、表单、跳转等交互。
- 给出状态模型、事件绑定和模拟数据结构。
- 明确哪些交互只做静态展示，哪些需要可操作。

### 7.5 模块整合 AI

输入：

- 所有模块计划。
- `page-layout.json`
- `page-layout.md`

输出：

- `assembly.plan.md`

职责：

- 决定最终文件结构。
- 统一全局 CSS 变量、字体、断点、容器宽度。
- 处理模块间重叠、背景连续性、滚动顺序、共享数据。
- 给最终代码生成提供可执行计划。

### 7.6 代码生成 AI

输入：

- `assembly.plan.md`
- 所有模块计划。
- 资源文件。
- 设计稿截图，可选

输出：

- `index.html`
- `styles.css`
- `script.js`
- 复制后的静态资源。

职责：

- 生成高保真 HTML 页面。
- 保证资源引用可用。
- 保证主要交互可运行。
- 根据截图比对报告迭代修正。

## 8. 功能需求

### 8.1 导出链路

- 插件 GUI 必须提供“一键生成 HTML”的主入口。
- 插件提交任务前必须检查 MCP/本地任务服务连通性。
- 用户可选择仅导出结构、导出原图、导出渲染切片，或一键生成 HTML。
- 默认只导出结构和资源引用，避免大图导致首轮卡顿。
- 默认主路径应尽快提交任务并关闭插件，不能依赖隐藏 UI 或缩小窗口来释放画布。
- 插件提交任务后必须保存 `jobId`，支持重开插件继续查询任务状态。
- 外部面板必须支持根据 `jobId` 查看实时进度、日志摘要和最终下载入口。
- 当前页面所有 Frame 一键导出时，默认只能导出结构和资源引用。
- 原图和渲染切片必须支持按需补导，不应默认全量导出。
- 渲染切片不能默认按 `imageRef` 自动批量生成完整资源集，后续应由 `asset-export-plan.json` 指定需要切片的节点。
- 插件内短任务可显示阶段、数量、当前文件或节点名称；插件外长任务进度由外部面板展示。
- 单个原图和切片导出必须有超时、错误记录和降级状态。
- 导出结果必须包含缺失资源统计和错误详情。
- 资源导出应支持后续增量补导，不要求一次性全部完成。

### 8.2 任务编排与状态面板

- MCP/本地服务必须提供创建任务、查询任务、查询日志、下载产物的接口。
- 插件通过本地 HTTP/WebSocket bridge 创建任务，不直接调用 stdio MCP。
- 创建任务接口必须接收插件采集到的 `raw.json`、`asset-manifest.json`、导出配置和源页面摘要。
- 任务状态必须持久化到本地目录，服务重启后可以恢复或至少读取最后状态。
- 外部面板必须支持 `queued`、`running`、`done`、`error`、`canceled` 的状态展示。
- 外部面板必须展示当前阶段、百分比、更新时间、错误摘要和输出路径。
- 插件重新打开时必须能读取最近任务，并在服务可用时同步最新状态。
- 如果 MCP/本地服务未启动，插件应给出启动说明或降级为仅导出 ZIP 的离线模式。

### 8.3 标准化链路

- 支持从 `raw.json` 生成 `raw.normalized.json`。
- 过滤不可见节点、无效样式和冗余字段。
- 保留完整节点 ID、节点名称、节点类型和父子关系。
- 补全图片资源和 `assetId` 的引用关系。
- 标记文本、图片、容器、列表、装饰、背景等候选语义。
- 提取可生成 CSS 的视觉字段，不仅保留文字和亲子结构。
- 输出页面级 `design-tokens.json`，并在模块切片中保留模块局部样式。
- 输出 `asset-index.json` 和 `asset-export-plan.json`，为按需补导关键资源做准备。
- 标记 `slice-candidate` 时必须说明切片原因、目标节点、边界策略和失败降级。

### 8.4 布局分析

- 识别页面主轴方向和模块顺序。
- 识别 Header、Hero、内容区、列表区、Footer 等常见模块。
- 识别绝对布局中的相对关系，例如居中容器、等距列表、左右栏、卡片网格。
- 输出机器可读 JSON 和人工可读 Markdown。

### 8.5 模块切片

- 按模块生成独立 `module.json`。
- 每个模块保留源节点集合、边界、文本、图片、样式摘要、布局约束、状态样式。
- 支持重复结构合并，例如多个相同职位卡片归并为一个 `itemPattern`。
- 支持对不确定模块打标，等待人工确认或 AI 二次判断。

### 8.6 多角色计划生成

- 每个模块至少生成组件计划、资源计划、交互计划。
- 计划必须可追溯到模块 ID、节点 ID 和资产 ID。
- 计划中必须明确实现方式、风险点、降级策略和验收标准。

### 8.7 代码生成与组装

- 支持生成纯 HTML/CSS/JS 的单页产物。
- 生成结果必须能在本地浏览器直接打开或通过本地静态服务预览。
- CSS 应优先使用正常文档流、flex、grid、相对定位；仅对装饰层、特殊重叠区域使用 absolute。
- 图片引用必须优先使用 `copiedPath`，缺失时按资源计划降级。
- 交互逻辑应集中在 `script.js` 或 HTML 内联脚本中，保持可读性。

### 8.8 视觉 QA

- 支持导入或生成设计稿整体截图。
- 支持对生成页面截图。
- 输出视觉差异报告，包括尺寸、模块位置、主要颜色、图片缺失、文本溢出、明显错位。
- 支持基于差异报告进行一轮或多轮修正。

## 9. 性能与稳定性要求

- 插件不应承载 AI 计划、HTML 生成、视觉 QA 等长任务。
- 插件提交任务后应尽快调用 `closePlugin()`，释放 MasterGo 画布控制权。
- 插件侧采集必须控制在短耗时范围内，默认不做全量大图和全量切片导出。
- 长任务进度必须由外部面板展示，插件重新打开时可查询最近任务状态。
- 单个图片读取和切片导出必须有超时保护。
- 大图导出应支持跳过、按需导出和失败重试。
- 不允许把全页面多 Frame 的全量静态资源导出作为默认同步流程。
- 资源导出应限制并发，避免 MasterGo 或浏览器环境卡死。
- ZIP 打包前应估算文件数量和资源体积，并在 UI 中给出提示。
- 导出失败不得丢失已完成的结构数据。
- AI 工作流应支持从任意阶段产物恢复，不必从 MasterGo 重新导出。
- MCP/本地服务应持久化任务状态、阶段日志和输出路径。

## 10. 验收标准

首个可用闭环验收：

- 能从选中 Frame 导出 `raw.json`、`asset-manifest.json` 和可选资源。
- 能在插件 GUI 点击“一键生成 HTML”，由插件采集任务输入并提交到 MCP/本地服务。
- 能从插件提交任务到 MCP/本地服务，拿到 `jobId` 并关闭插件释放画布。
- 能通过外部面板查看实时进度、日志摘要和最终下载入口。
- 能重新打开插件读取最近 `jobId` 并展示任务状态。
- 能生成 `page-layout.json`、`page-layout.md`。
- 能按模块生成 `*.module.json`。
- 能为每个模块生成三个计划文件。
- 能生成 `assembly.plan.md`。
- 能生成可预览的 `index.html`、`styles.css`、`script.js`。
- 在至少一个真实页面样例上，主要模块顺序、视觉层级、图片、文本、间距接近设计稿。
- 长任务执行期间 MasterGo 画布可继续操作，失败资源有明确状态和错误记录。

## 11. 风险

- MasterGo 节点树命名不规范会影响模块识别准确率。
- 绝对布局转相对布局存在语义推断误差。
- 图片资源导出速度受 MasterGo API、图片体积和网络/本地环境影响。
- 插件隐藏 UI 不能保证释放画布控制权，因此不能作为后台运行方案。
- MCP/本地服务需要额外安装、启动和权限配置，可能增加首轮使用成本。
- 插件关闭后不能继续调用 `mg` API，所有依赖当前文档上下文的补导都必须在关闭前完成，或通过重新打开插件触发。
- AI 计划如果只使用 Markdown，容易丢失可追溯性；如果只使用 JSON，模型理解和人工审查成本较高。
- 最终 HTML 高保真程度依赖截图比对和迭代修正能力。

## 12. 推荐优先级

P0：

- 稳定导出链路。
- 建立插件提交任务、外部面板进度、插件重开查状态的任务闭环。
- 解决长任务占用画布控制权的问题。
- 固定中间产物 schema。
- 生成页面布局与模块切片。

P1：

- 多角色 AI 计划生成。
- 模块整合计划。
- 纯 HTML/CSS/JS 生成。

P2：

- 自动截图比对和迭代修正。
- 人工审查 UI。
- 多页面和组件库扩展。
